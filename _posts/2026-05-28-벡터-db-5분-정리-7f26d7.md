벡터 DB 라는 게 뭐 하는 물건인지 한 번 정리해두고 싶었다. RAG 파이프라인을 두어 번 만들면서 매번 같은 자리에서 멈칫하길래, 차라리 글로 박아두자 싶었거든.

먼저 한 줄 비유부터. 일반적인 RDB — MySQL 이나 PostgreSQL — 가 "title 이 '벡터 DB' 인 글 찾아줘" 식의 정확 검색이라면, 벡터 DB 는 "이 글이랑 분위기 비슷한 거 찾아줘" 식 검색을 한다. 단어가 안 겹쳐도 의미가 가까우면 잡아내는 게 포인트. SQL 의 LIKE 로는 죽었다 깨어나도 못 잡는 결.



핵심은 **임베딩(embedding)**. 글이든 이미지든 어떤 모델을 통과시키면 길이 768 이나 1536 정도의 숫자 벡터로 변환되는데, 이 벡터들 사이의 거리(코사인 유사도 같은 것)가 의미적 유사도랑 대충 비례한다고 본다. 그래서 "비슷한 글 찾기" 가 결국 "벡터 공간에서 가까운 점 찾기" 문제로 바뀌어버리는 거.

근데 막상 1000만 개 벡터에서 가장 가까운 10개를 전수 비교로 찾으려고 들면? 죽어버린다. 정확히는 안 죽는데 너무 느려서 의미가 없어지는 수준. 그래서 **ANN(Approximate Nearest Neighbor)** 알고리즘이 등장. HNSW, IVF, PQ 같은 인덱스들이 그건데, 이름이 무섭게 생겼어도 핵심은 "정확도 1~2% 양보하고 100배 빠르게" 정도의 트레이드오프야.

HNSW 가 요즘 사실상 기본값처럼 쓰이는 인상. 그래프 기반이라 메모리는 좀 먹는데, 검색이 빠르고 동적 추가가 쉬워서. 정확한 수치는 기억이 흐릿한데, 내 환경에서 100만 벡터에 HNSW 깔고 top-10 검색이 5ms 안쪽이었던 거 같다 (1536 차원, M=16 기준).

전체 흐름을 한 번 그려보면 이런 모양.

```mermaid

  LLM --> Ans[최종 답변]
```

이게 RAG 의 기본 골격이고, 벡터 DB 는 이 그림에서 정중앙에 앉아 있는 셈. LLM 한테 "이 질문 답하기 좋은 자료 몇 개 찾아왔어, 참고해서 답해줘" 라고 들이미는 그 자료 검색을 담당.

선수들을 짧게 보면, **Pinecone** 이 매니지드 SaaS 쪽 대표. 인프라 신경 쓰기 싫고 빨리 돌리고 싶을 때 고르는 옵션. **Qdrant** 는 Rust 로 쓰인 오픈소스인데 셀프호스팅 운영해본 한에선 안정적이었던 인상. **Weaviate** 는 GraphQL 인터페이스가 호불호 갈리는 듯하고, **Chroma** 는 로컬 개발용으론 거의 표준에 가깝게 자리잡았더라. 그리고 **pgvector** — Postgres 확장으로 벡터 검색을 붙이는 거. 이미 Postgres 쓰는 팀이라면 새 인프라 들이는 것보다 이게 합리적일 때가 많은 것 같음.

```python
# CREATE EXTENSION vector;
# CREATE TABLE docs (id serial, embedding vector(1536));

cur.execute(
    "SELECT id FROM docs ORDER BY embedding <=> %s LIMIT 5",
    (query_vec,)
)
```

`<=>` 가 코사인 거리 연산자. SQL 안에서 그냥 ORDER BY 로 자연스럽게 풀리는 게 매력. 다만 수천만 벡터 단위로 가면 전용 벡터 DB 가 더 빠른 경우가 많다는 게 일반적인 평인 듯.

솔직히 만져보면서 가장 짜증났던 건 **임베딩 모델 갈아끼우는 순간**. text-embedding-3-small 에서 다른 모델로 바꾸면 차원도 다르고 의미 공간 자체가 달라서, 인덱스를 통째로 재구축. 데이터 100만 건이면 임베딩 비용도 다시 든다. 그래서 모델 선택은 처음에 좀 신중히 — 라는 게 비싸게 배운 교훈.

또 하나, 벡터 검색은 **의미적으로 가까운** 걸 찾아주지 **정답** 을 찾아주는 게 아니라는 점. RAG 가 자꾸 헛소리하는 이유의 절반은 검색이 적당히 비슷한 무관한 문서를 끌어와서 LLM 이 거기에 휘둘리는 거고. 그래서 요즘은 BM25 같은 키워드 검색이랑 벡터 검색을 섞는 **하이브리드** 가 거의 기본처럼 자리잡는 분위기.

여기까지가 5분 정리. 더 들어가면 quantization, multi-vector, late interaction(ColBERT 류) 같은 토끼굴이 줄줄이 있는데, 그건 다음 글에. 일단 벡터 DB 가 뭐 하는 물건인지 감 잡는 데는 이 정도면 충분하지 않을까 싶음.
