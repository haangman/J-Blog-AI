벡터 검색 얘기를 하다 보면 결국 "코사인 유사도(cosine similarity)" 랑 거리 함수로 돌아오게 되더라. RAG — 검색해서 가져온 문서를 LLM 한테 같이 던져주는 그 방식 — 를 만지다 보면 "이 질문이랑 가장 가까운 문서가 뭐냐" 를 계산해야 하는데, 그 '가까움' 을 재는 자가 바로 이것들이거든.

사실은 비유가 제일 빠르다. 단어든 문장이든 임베딩 모델을 통과시키면 숫자 배열, 그러니까 벡터가 하나 튀어나온다. 화살표라고 생각하면 편하지. 원점에서 어딘가를 가리키는 화살표. 두 화살표가 비슷한 방향을 가리키면 의미가 비슷한 거고, 영 딴 데를 가리키면 상관없는 내용인 거야.

근데 여기서 갈린다. 두 화살표의 **방향** 만 볼 거냐, **실제 떨어진 거리** 까지 볼 거냐.

코사인 유사도는 오로지 방향만 본다. 두 화살표 사이 각도가 0도에 가까우면 1, 직각이면 0, 정반대면 -1. 화살표가 얼마나 긴지는 아예 무시하지. 반대로 유클리드 거리(Euclidean distance) — 우리가 자로 두 점 사이를 재는 그 거리 — 는 길이까지 다 따진다.

이게 좀 웃긴 게, 텍스트 임베딩에서는 거의 항상 코사인을 쓴다. 왜냐면 문서가 길든 짧든 '의미의 방향' 만 맞으면 비슷하다고 보고 싶거든. "고양이는 귀엽다" 와 "고양이는 정말정말 너무너무 귀엽다" 가 길이 때문에 멀어지면 곤란하잖아.

코드로는 사실 한 줄이야. 정규화된 벡터끼리는 내적(dot product)이 곧 코사인 값이 되거든.

```python
import numpy as np

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))
```

내가 실제로 벡터 DB 만지면서 헷갈렸던 지점 하나. 어떤 라이브러리는 '유사도' 가 아니라 '거리' 로 결과를 준다. 코사인 거리 = 1 − 코사인 유사도. 그래서 값이 작을수록 가까운 거라 부호 감각이 반대로 돌아간다. 처음엔 이걸 모르고 top-k 를 거꾸로 뽑아서 엉뚱한 문서가 올라온 적도 있었지. 정렬 방향 한 번씩 꼭 확인하는 게 마음 편하더라.

그럼 코사인이 항상 정답이냐. 그건 또 아닌 것 같다. 추천 시스템처럼 '크기' 자체가 신호인 경우 — 이를테면 사용자가 얼마나 많이 봤느냐 — 라면 길이를 버리는 코사인이 오히려 정보를 깎아먹을 수도 있고. 내적을 그냥 그대로 쓰는 경우도 있더라. 결국 "내 데이터에서 뭐가 '가깝다' 의 의미냐" 를 먼저 정해야 도구가 정해지는 셈인데, 이 감각은 한두 번 직접 틀려봐야 손에 붙는 것 같다.
