HN 메인을 훑다가 'Tiny-vLLM' 이라는 글이 눈에 띄었는데, 같은 날 'Real-time LLM Inference on Standard GPUs: 3k tokens/s per request' 라는 글도 같이 올라왔더라. LLM 추론 가속 — 큰 모델을 어떻게 더 빠르게, 더 싸게 굴릴까 하는 문제 — 가 요즘 별도의 분야로 굳어지는 분위기네.

작년만 해도 다들 '몇 B 짜리 모델이 또 나왔다'에 흥분했지. 근데 사실은 그 흐름이 슬슬 꺾이고 있는 것 같다. GPT-5 든 Claude 4 든 누군가는 또 만들고 있겠지만, 정작 시장의 무게는 '얼마나 큰가' 보다 '얼마나 싸게 빠르게 돌리느냐' 쪽으로 옮겨가는 게 보이거든.

내가 회사에서 하는 일도 사실 모델 학습보단 **남이 만든 모델을 어떻게 production 에 안 죽이고 꽂아 넣느냐** 쪽이다. 그러다 보니 vLLM 같은 추론 엔진(요청을 모아서 GPU 에 효율적으로 흘려주는 미들웨어) 을 자주 만지게 되거든. '추론 엔진이 도대체 뭐 하는 물건인가' 라는 질문이 처음엔 좀 막연했지.

거칠게 비유하자면 GPU 라는 비싼 부엌 한 칸에서 1000 명 손님 주문을 동시에 받아내는 식당 운영 문제와 비슷한 거. 순서대로 한 명씩만 받았다간 부엌이 노는 시간이 너무 많아져서 망해. 그래서 등장한 게 KV cache 관리(이전 토큰의 중간 계산을 기억해 재활용), continuous batching(새 주문이 들어오면 도중에 끼워 넣기), PagedAttention(메모리를 페이지 단위로 쪼개 관리) 같은 기법들. vLLM 이 PagedAttention 으로 유명해진 게 2023 년쯤이었던 것 같다.

그 vLLM 이 이제는 Python+CUDA 의존성이 무거워서 임베디드나 작은 서비스에는 부담이라는 불만이 나왔고, Tiny-vLLM 처럼 'C++/CUDA 만으로 다시 쓴' 프로젝트가 등장하는 흐름. 내가 직접 빌드해 본 건 아니라 성능 수치를 단정하긴 어려운데, 적어도 의도는 분명히 읽힌다 — **적은 의존성 + 최적화된 커널 = 더 가볍게 띄울 수 있는 추론 서버**.

같은 날 같이 올라온 '3k tokens/s per request' 글. 요청당 초당 3천 토큰이라는 숫자는 체감상 좀 비현실적이긴 한데, 작은 모델이거나 speculative decoding(보조 모델이 미리 다음 토큰들을 예측해 한꺼번에 검증하는 기법) 같은 트릭을 쓴 게 아닐까 싶다. 정확한 셋업을 확인 못 했으니 일단 '그런 시도가 나오고 있다' 정도로 받아들이는 게 맞을 듯.

내가 본 한에선, 추론 엔진 내부의 흐름은 대략 이런 식이다.

```mermaid
graph LR
  요청["사용자 요청"] --> 큐["배치 큐"]
  큐 --> KV["KV 캐시 관리"]
  KV --> 커널["CUDA 커널"]
  커널 --> 출력["스트리밍 응답"]
  큐 -. 도중 합류 .-> KV
```

각 단계를 얼마나 알뜰하게 짜느냐가 곧 비용. 배치 큐에 새 요청을 도중에 끼워 넣을 수 있느냐, KV cache 를 페이지 단위로 재활용할 수 있느냐, CUDA 커널이 GPU 코어를 놀리지 않게 fuse 됐느냐 — 이런 디테일이 결국 token/s 차이로 직결된다.

체감으로 적자면, 작년 이맘때만 해도 'A100 한 장에 7B 모델 띄워서 서비스로 굴린다' 가 자랑할 만했지. 요즘은 RTX 4090 한 장에 13B 도 적당히 굴린다는 글이 종종 올라오더라. 내 환경 — RTX 4080 — 에서도 7~9B 정도는 큰 무리 없이 인터랙티브하게 도네.

이런 흐름이 의미하는 게 뭐냐 하면, **모델을 직접 학습할 능력은 없어도 남이 만든 모델을 자기 인프라에서 굴릴 수 있는 영역이 점점 넓어진다는 것**. 스타트업이나 1인 개발자가 API 비용 안 내고 자기 서버에서 LLM 을 굴리는 그림. 나 같은 회사원이 보기엔 '와 좋네' 와 '근데 진짜 production 까지 갈까?' 사이의 어딘가.

물론 한계도 분명히 있다. 3k tokens/s 같은 수치는 거의 항상 '작은 모델 + 짧은 컨텍스트 + 특정 디코딩' 조건이 붙어 있는 경우가 많고, 실제 운영 상황(다양한 사용자가 긴 컨텍스트로 동시 접속) 에선 그만큼 안 나오는 게 보통이거든. Tiny-vLLM 같은 신생 엔진도 GitHub 별 개수만 보고 production 에 도입했다가 미묘한 버그가 잡혔을 때 직접 들여다볼 사람이 없으면 곤란해지고.

그래도 방향 자체는 분명한 것 같다. 큰 모델은 큰 모델대로 계속 나오겠지만, 그 옆에서 **'어떻게 더 싸게 빠르게'** 라는 질문에 매달리는 사람들이 한 분야를 만들어가는 중. 이게 어디까지 갈지는 좀 더 봐야 알 듯하다.
